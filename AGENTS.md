# Инструкции проекта

## Обязательная процедура создания коммита

Перед каждым `git commit` или `git commit --amend`:

1. Повторно прочитай раздел «Именование коммитов» ниже.
2. Получи имя текущей Git-ветки и проверь сообщение коммита на соответствие указанному формату.
3. Не создавай коммит, если сообщение не соответствует формату.

## Именование коммитов

Используй следующий формат названия коммита:

```text
<ветка>:<описание изменений на английском>
```

Вместо `<ветка>` указывай имя текущей Git-ветки. Описание изменений пиши на английском языке.

Пример:

```text
feature/campaign-products:Add editable product margin settings
```

## Актуальность README

При изменении конфигурации, структуры, команд, потоков данных или поведения,
которые уже описаны в `README.md`, обязательно обновляй соответствующий раздел
README в рамках той же задачи.

Не добавляй в README детали, которых нет в фактической реализации. Перед
завершением работы сверяй изменённую реализацию с существующим описанием.

## Публичные границы модулей и импорты

Это правило одинаково применяется к backend и frontend.

1. Каждый самостоятельный модуль или feature предоставляет публичный API через
   корневой `index`-файл. Если внутри модуля есть логические группы с несколькими
   экспортами (`components`, `decorators`, `guards`, `hooks`, `services` и
   подобные), создавай для них собственные `index`-файлы и собирай нужные
   публичные экспорты в корневом `index` модуля.
2. Код за пределами модуля импортирует его сущности только через публичную точку
   входа модуля, предпочтительно через настроенный alias. Не используй внешние
   deep-imports во внутренние файлы или подпапки модуля.
3. Код внутри самого модуля использует относительные импорты либо локальные
   `index`-файлы. Не импортируй внутренние зависимости через публичный alias
   собственного модуля, чтобы не создавать циклические зависимости через его
   корневой `index`.
4. Не объединяй в одном корневом barrel экспорты, совместная загрузка которых
   создаёт runtime-цикл. В частности, module/component entrypoint и используемые
   инфраструктурой runtime-сущности при необходимости разделяй на отдельные
   публичные точки (`#feature` и `#feature/entities`, `@/feature` и
   `@/feature/model`). Type-only экспорты оформляй через `export type`.
5. При создании, перемещении, переименовании или удалении файлов обязательно:
   - найди все старые импорты и экспорты;
   - обнови публичные и локальные `index`-файлы;
   - проверь package aliases, TypeScript paths и mappings тестового runner;
   - убедись поиском, что устаревших путей и запрещённых deep-imports не осталось;
   - выполни typecheck, сборку и относящиеся к изменению тесты;
   - при изменении `index`/barrel или ESM-графа импортов выполни runtime smoke
     test собранного приложения: typecheck и build не обнаруживают ошибки
     инициализации циклических ESM-зависимостей.
6. При работе с любым файлом проверяй его существующие импорты и экспорты на
   соответствие этому правилу. Обнаруженные нарушения в обрабатываемых файлах
   исправляй в рамках той же задачи; нарушения вне области задачи явно отмечай,
   если безопасное исправление потребует дополнительных изменений.
